# WK-0015: Add a tracked version so consuming repos know when a full upgrade is needed

## Description

When `kb` is deployed into consuming repos and the `kb` checkout is updated via `git pull`,
there is currently no way to determine whether the new code is compatible with the existing
consuming-repo surface or whether a full upgrade runbook (`docs/upgrade-consuming-repo.md`)
needs to be run.

A version marker — tracked somewhere in `kb` and stamped into the consuming repo at
`sync-contract` or `init-config` time — would let operators compare the deployed version
against the current `kb` version and decide whether a lightweight pull is sufficient or
a full upgrade pass is required.

## Acceptance Criteria

- [ ] `kb` tracks a version (semver or monotonic) in a well-known location
- [ ] `sync-contract` or another deploy-time command stamps the deployed version into the consuming repo
- [ ] There is a quick check (CLI command or convention) that compares deployed vs current and reports whether an upgrade is needed
- [ ] `docs/upgrade-consuming-repo.md` references the version check as a pre-step

## Open Questions

- Where should the version live? `package.json`, `contract/manifest.json`, or a dedicated `VERSION` file?
- Should the check be a `dispatch` subcommand, a `wiki` subcommand, or standalone?
- Should breaking changes bump a major version, or is a monotonic "schema version" for the contract surface sufficient?
