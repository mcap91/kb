# DEC-0901: Same-repo integration defaults to a direct import

## Context

Two modules living in the same repo sometimes need one to call the other. In the past this repo has reached for
a server boundary (an MCP server, an HTTP endpoint) even when both sides run in the same process and the same
deploy.

## Decision

A caller and callee in the same repo integrate through a direct library import. A server boundary — MCP or
otherwise — is reserved for a caller that runs out-of-process from the callee, or that lives in a different
repo.

## Rationale

The simplest option with the least blast radius wins by default. A direct import carries no network hop, no
extra process to deploy, and no new contract to version; a server boundary earns its cost only when the caller
genuinely cannot import the callee's code.

## Consequences

Any same-repo integration proposal that reaches for a server boundary must first show why a direct import does
not work, not the reverse.

## Alternatives Considered

- **MCP server for every cross-module call.** Rejected: adds a process, a contract and a network hop for calls
  that could be a function call.
- **Case-by-case choice with no standing rule.** Rejected: this is exactly the kind of question that keeps
  reaching the operator; a standing default removes the repeat.
