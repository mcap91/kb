# DEC-0903: Export jobs retry a transient failure, fail fast on a non-transient one

## Context

An export run can fail for reasons that clear on their own (a dropped connection, a momentary timeout) and for
reasons that will not clear without a human fixing something (a malformed connector record, an authorization
error). Each export job previously picked its own answer ad hoc.

## Decision

Every export job retries a transient failure (network and timeout errors) with backoff, up to a fixed retry
count. A non-transient failure (a malformed record, an authorization error) fails the run immediately with no
retry.

## Rationale

Retrying a transient failure recovers most real-world flakiness for free. Retrying a non-transient failure
only delays the same certain failure and hides it behind retry noise.

## Consequences

Every export job classifies its own failures into transient or non-transient before this rule applies to it.

## Alternatives Considered

- **Never retry.** Rejected: throws away runs that would have succeeded on a second attempt.
- **Retry everything the same number of times.** Rejected: wastes time and obscures non-transient failures
  that need a human, not a retry.
