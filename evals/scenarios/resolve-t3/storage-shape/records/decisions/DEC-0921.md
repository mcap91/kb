# DEC-0921: Structured lists live in a body table, not nested frontmatter

## Context

A record sometimes needs an ordered, structured list — more than a flat array of strings. The scheduler's
per-pipeline step list is one case. Nested frontmatter YAML (a list of maps) looked like an option.

## Decision

A structured list that needs more than one field per entry is written as a markdown table under a body
heading, never as nested frontmatter YAML.

## Rationale

The comparable systems in this repo that already hold a structured list keep it as a body table, never as
nested frontmatter; none of this repo's record types use nested frontmatter YAML anywhere. The frontmatter
parser does not support nested YAML ([[WK-0923]]), and a graph or index pass that reads frontmatter fields
generically would misread nested keys as top-level fields. A body table needs no parser change and renders
directly.

## Consequences

Any future structured-list need (steps, stages, rows) follows the same body-table shape; nested frontmatter
YAML is not an option to propose again without first overturning this decision.

## Alternatives Considered

- **Nested frontmatter YAML.** Rejected: no parser in this repo reads it correctly ([[WK-0923]]); would also
  corrupt any pass that reads frontmatter fields generically.
- **A separate file per list.** Rejected: more moving parts than a table in the same record, for no gain here.
